# 首关与结算性能检查（2026-10-07）

## 结论与本次修改

代码与资源静态检查发现可优化路径，但尚未取得微信真机 Profiler 数据，不能把某一项认定为实际卡顿的唯一原因。

1. **首关引导预加载**：GameManager 读完存档后，异步预读 UICorePlay、GameViewRoot；只有待进入第1关且引导未完成时预读 UIGuide。进入玩法时再次调用相同入口，覆盖重置、跳关和失败重试。已有加载中的请求不会重复发起。
2. **结算预加载**：首页及启动完成事件后开始预读 UIFinish；进入玩法也有兜底。预读仅持有预制体及静态依赖的资源句柄，不调用 ShowUI，不触发结算埋点、广告页面状态、奖励展示或引导完成状态。管理器释放时归还句柄。
3. **笔画创建**：DrawAsync 之前仅在开始处 await，之后全部笔画在一帧内完成网格生成和碰撞体创建。现在按约3ms的时间预算在笔画之间切到下一帧，恢复时检查销毁与绘制版本。复用顶点数组并原地翻转三角形绕序，减少临时 List 和 ToArray 分配。保留原剖分算法、碰撞体规则和笔画索引。
4. **引导高亮**：此前每帧额外调用 Camera.Render，目标纹理与屏幕同尺寸。现在复用静止画面，只在切换笔画、颜色变化、世界变换/相机矩阵变化、分辨率变化时重绘，保持动画期间跟随。

### 优化边界

- 预加载不是预实例化。窗口首次 Instantiate、ScriptGenerator、布局/字体网格生成仍在打开时发生；动态图标（UIFinish.LoadRewardIconAsync）不一定属于预制体依赖。
- 预加载提前占用资源内存，当前最多保留5个预制体地址的句柄，资源体积需真机测量。窗口原有 CacheOnClose 已默认开启，因此后续打开本就可以复用实例。
- 3ms是笔画之间的软预算，单根复杂笔画的剖分或碰撞体创建仍可能超过它；总计算量不会因分帧减少。
- 高亮仍分配全屏 RenderTexture。若首次创建纹理依然造成峰值，可在实测后限制纹理分辨率或预热纹理，但需检查高分屏笔画边缘。
- 结算前原有700ms等待用于最后答案入槽动画，本次保留。这段有意的等待不属于资源加载耗时。

### 需要特别核对的打包配置

`Assets/Editor/AssetBundleCollector/AssetBundleCollectorSetting.asset` 中，Fonts 使用 **PackCollector**，UI 使用 **PackSeparately**。
同目录 `AssetBundleCollectorConfig.xml` 对应规则仍是 **PackDirectory**。两份配置不一致，后续若从XML导入，可能改变当前打包粒度。

字体集中打包可能让首次使用任意字体时需要取得较大的字体Bundle，但并不等于所有字体同时解码到内存。本次没有改打包规则；先依据实际Bundle报告、依赖图和发布流程决定是否拆包，避免改完被另一份配置覆盖。

大背景已有WebGL平台覆盖（textureFormat=50）、关闭MipMap、关闭Read/Write。因此“再压一次PNG”不能直接等同于缩小运行纹理或改善GPU上传；应以Unity/微信构建报告和真机数据为依据。

## 下一轮笔画优化方向

- 将三角剖分结果、简化碰撞轮廓在编辑器生成时烘焙，运行时只组装Mesh/Collider。能消除运行时计算，但会增加配置格式和资源维护成本，需要全关卡几何验证。
- 跨关笔画对象池、共享材质配合逐笔画颜色参数：当前每根笔画创建独立Material，仍可优化；必须验证独立高亮、引导相机和渲染批次，不宜直接合并材质导致全字同色。
- 当前同字几何已有复用缓存，不需要重复添加另一套无界缓存。
